## 2. 前提

MVP では、以下の責務分担を前提にする。

- GitHub Actions 上の Docker Action が KiCad 成果物を生成する
- SaaS は成果物の受信、保存、表示、差分判定、GitHub Issue 連携を担当する
- API 契約は Rust の handler / schema から生成する OpenAPI を中心に管理する
- サーバーは Rust、フロントエンドは Next.js を基本方針とする
- DB は PostgreSQL を主データストアにする
- Redis はキャッシュではなく、主にジョブ補助・レート制御・短期状態管理に使う

## 3. 全体アーキテクチャ

```text
GitHub Actions (Docker Action)
  -> OpenAPI-based SaaS API
  -> presigned upload to staging object storage
  -> import request to SaaS API

SaaS
  - Next.js frontend
  - Rust API server
  - Rust worker
  - PostgreSQL
  - Redis
  - S3-compatible object storage
```

この構成では、成果物生成の重い処理を GitHub Actions 側に閉じ込めつつ、SaaS 側は状態管理、閲覧体験、GitHub 連携に集中できる。

## 4. 決定済みの技術方針

| 領域 | 採用方針 |
|---|---|
| API 契約 | OpenAPI 3.1.0 generated by utoipa |
| Backend | Rust + Axum + utoipa |
| DB | PostgreSQL + SQLx |
| Worker | PostgreSQL backed queue |
| Redis | rate limit / debounce / lock / short-lived state |
| Artifact 保存 | S3-compatible object storage + staging zip import |
| Artifact preview | viewer-sources API + KiCanvas + PDF/SVG fallback |
| Frontend | Next.js App Router + TypeScript |
| UI | Chakra UI + lucide-react |
| 認証 | GitHub OAuth + GitHub App |
| インフラ | VPS |
| ローカル開発 | Docker Compose |
| 監視 | OpenTelemetry + structured logging |

## 5. 境界の考え方

### Frontend に寄せるもの

- Repository / BoardProject / Run の一覧・詳細表示
- 成果物への導線、プレビュー、比較 UI
- GitHub 権限に基づく閲覧体験

### Backend に寄せるもの

- Rust code-first OpenAPI に基づく API 提供
- BoardProject / BoardRun / Artifact の永続化
- 差分判定、ジョブ管理、GitHub Issue 連携
- Artifact の認可付き配信
